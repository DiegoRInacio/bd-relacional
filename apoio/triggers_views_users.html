Triggers, Views e Usuários

Modelos prontos de PL/pgSQL, views e gestão de roles no PostgreSQL. Adapte os nomes ao seu cenário.

Cenário de exemplo

CREATE SCHEMA loja;

CREATE TABLE loja.produto (
    id     SERIAL PRIMARY KEY,
    nome   VARCHAR(100) NOT NULL,
    preco  NUMERIC(10,2) NOT NULL CHECK (preco > 0),
    estoque INT NOT NULL DEFAULT 0
);
CREATE TABLE loja.venda (
    id         SERIAL PRIMARY KEY,
    id_produto INT NOT NULL REFERENCES loja.produto(id),
    quantidade INT NOT NULL CHECK (quantidade > 0),
    data_venda TIMESTAMP NOT NULL DEFAULT NOW()
);

TRIGGERS

Uma trigger tem duas partes

  1. a função em PL/pgSQL — contém a lógica, retorna TRIGGER;
  2. o CREATE TRIGGER — liga a função a uma tabela, um evento e um momento.

Função — template

CREATE OR REPLACE FUNCTION loja.fn_log_venda()
RETURNS TRIGGER AS $$
BEGIN
    -- lógica aqui; os dados da linha chegam por NEW (e/ou OLD)
    INSERT INTO loja.log_venda (id_venda, quantidade, usuario_bd, momento)
    VALUES (NEW.id, NEW.quantidade, CURRENT_USER, NOW());

    RETURN NEW;   -- AFTER: obrigatório, não altera a linha
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER

CREATE TRIGGER trg_log_venda
AFTER INSERT ON loja.venda      -- momento (BEFORE/AFTER) + evento + tabela
FOR EACH ROW                    -- uma vez por linha afetada
EXECUTE FUNCTION loja.fn_log_venda();

-- pode combinar eventos:  AFTER INSERT OR UPDATE ON ...
-- remover:                DROP TRIGGER trg_log_venda ON loja.venda;

Bloquear uma operação — BEFORE + RAISE EXCEPTION

CREATE OR REPLACE FUNCTION loja.fn_checa_estoque()
RETURNS TRIGGER AS $$
BEGIN
    IF NEW.quantidade > (SELECT estoque FROM loja.produto WHERE id = NEW.id_produto) THEN
        RAISE EXCEPTION 'Estoque insuficiente para o produto %', NEW.id_produto;
    END IF;
    RETURN NEW;   -- BEFORE: RETURN NEW deixa a operação seguir
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_checa_estoque
BEFORE INSERT ON loja.venda
FOR EACH ROW EXECUTE FUNCTION loja.fn_checa_estoque();

Como projetar a tabela de log

  • Sem FK — a referência é lógica (INT, não REFERENCES): o log tem que sobreviver se a venda for apagada.
  • Snapshot — guarde também os valores da época (nome, preço), para o log continuar legível.
  • Append-only — só a trigger insere: REVOKE UPDATE, DELETE ON loja.log_venda FROM ...
  • Nunca deleta linha de log — se precisar espaço, arquiva.
Evite: FK com ON DELETE CASCADE num log — apagar a venda apagaria o registro de auditoria dela.
CREATE TABLE loja.log_venda (
    id_log     SERIAL PRIMARY KEY,
    id_venda   INT,                 -- sem FK (referência lógica)
    quantidade INT,
    usuario_bd VARCHAR(50),
    momento    TIMESTAMP DEFAULT NOW()
);

VIEWS

CREATE VIEW

-- guarda um SELECT com um nome; não guarda dados
CREATE VIEW loja.vw_vendas_detalhe AS
SELECT v.id, p.nome AS produto, v.quantidade,
       v.quantidade * p.preco AS total
FROM   loja.venda  v
JOIN   loja.produto p ON p.id = v.id_produto;

-- usar como tabela
SELECT * FROM loja.vw_vendas_detalhe WHERE total > 500;

-- trocar a lógica sem recriar (preserva os GRANTs)
CREATE OR REPLACE VIEW loja.vw_vendas_detalhe AS SELECT ...;
A view sempre reflete as tabelas base — não existe "atualizar a view". Usos: esconder um JOIN grande, padronizar um cálculo, controlar acesso.

View materializada

CREATE MATERIALIZED VIEW loja.mv_faturamento AS
SELECT date_trunc('month', data_venda) AS mes,
       SUM(quantidade) AS itens
FROM loja.venda GROUP BY 1;

REFRESH MATERIALIZED VIEW loja.mv_faturamento;              -- recalcula
REFRESH MATERIALIZED VIEW CONCURRENTLY loja.mv_faturamento; -- sem travar leituras

INSTEAD OF — tornar a view gravável

Uma view simples (uma tabela, sem JOIN/GROUP BY) já aceita INSERT/UPDATE/DELETE. Uma view complexa precisa de um trigger INSTEAD OF que direciona a gravação para a tabela certa.

CREATE TRIGGER trg_ins_vw
INSTEAD OF INSERT ON loja.vw_vendas_detalhe
FOR EACH ROW EXECUTE FUNCTION loja.fn_insere_venda();

USUÁRIOS E PERMISSÕES

Criar role

CREATE USER ana WITH PASSWORD 'S3nh@Forte';   -- = CREATE ROLE ana LOGIN
CREATE ROLE leitura;                          -- role sem login: um "grupo"

-- \du  lista as roles     \password ana  troca a senha
AtributoSignifica
LOGINpode conectar (é um "usuário")
SUPERUSERignora todas as permissões — quase nunca use
CREATEDB / CREATEROLEpode criar bancos / outras roles

Permissão tem dois níveis

-- 1) chegar até as tabelas
GRANT CONNECT ON DATABASE loja TO ana;
GRANT USAGE   ON SCHEMA   loja TO ana;   -- SEM isso: "permission denied for schema loja"

-- 2) operar nas tabelas (próximo bloco)

GRANT nas tabelas

GRANT SELECT ON loja.produto TO auditor;                 -- uma tabela

GRANT SELECT, INSERT, UPDATE, DELETE
  ON ALL TABLES IN SCHEMA loja TO atendente;             -- todas as de agora

GRANT USAGE ON ALL SEQUENCES IN SCHEMA loja TO atendente; -- p/ o SERIAL no INSERT

-- tabelas criadas DEPOIS também:
ALTER DEFAULT PRIVILEGES IN SCHEMA loja
  GRANT SELECT ON TABLES TO leitura;
O dono da tabela já tem tudo. O GRANT serve para os outros.

Role de grupo — gerencie o grupo, não a pessoa

CREATE ROLE leitura;
GRANT USAGE ON SCHEMA loja TO leitura;
GRANT SELECT ON ALL TABLES IN SCHEMA loja TO leitura;

GRANT leitura TO ana, beto, carla;   -- entram no grupo e herdam as permissões

Mudou a regra? Ajusta a role leitura — os três já herdam.

REVOKE e testar

REVOKE INSERT ON loja.venda FROM atendente;
REVOKE ALL    ON ALL TABLES IN SCHEMA loja FROM ana;
REVOKE leitura FROM beto;            -- tira do grupo

-- testar sem sair da sessão:
SET ROLE auditor;
INSERT INTO loja.produto ...   -- ERRO: permission denied
RESET ROLE;

\dp loja.produto               -- ver os privilégios da tabela
Menor privilégio: comece com nada e vá liberando o necessário. A aplicação nunca conecta como SUPERUSER nem como o dono do banco.
