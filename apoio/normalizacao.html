Normalização passo a passo

Um exemplo resolvido do começo ao fim: de uma planilha bagunçada até um esquema em 3ª Forma Normal. Refaça este roteiro no seu próprio problema.

A planilha crua

Uma loja registra os pedidos numa tabela só — uma linha por item de pedido:

id_pedidoid_clinome_clientetelefone_clienteid_prodnome_produtoprecoqtd
1C1João Silva9999-1111, 3333-2222P1Notebook30001
1C1João Silva9999-1111, 3333-2222P2Mouse802
2C2Maria Lima8888-4444P3Smartphone20001
3C1João Silva9999-1111, 3333-2222P4Impressora8001
A chave desta tabela é o par (id_pedido, id_prod) — é o que identifica cada linha sem repetir.

As anomalias que essa estrutura causa

  • Inserção: não dá para cadastrar um produto novo (ou um cliente) sem que exista um pedido dele.
  • Alteração: o João mudou de telefone → é preciso corrigir todas as linhas dele.
  • Exclusão: apagar o pedido 2 apaga junto o único registro da Maria e do Smartphone.

Dependências funcionais

X → Y lê-se "sabendo X, o Y é sempre o mesmo". As desta planilha:

id_cli                 -> nome_cliente
id_prod                -> nome_produto, preco
id_pedido              -> id_cli
(id_pedido, id_prod)   -> qtd
-- telefone_cliente é multivalorado: id_cli ->> telefone

1ª Forma Normal — valores atômicos

Regra: cada célula guarda um único valor; sem grupos de colunas repetidos; cada linha identificável.

Problema: telefone_cliente guarda dois números.

Correção: o atributo multivalorado sai para uma tabela própria.

telefone_cliente
id_clitelefone
C19999-1111
C13333-2222

2ª Forma Normal — sem dependência parcial

Regra: estar em 1FN + toda coluna não-chave depende da chave inteira, não de um pedaço dela. (Só importa quando a chave é composta.)

A chave é (id_pedido, id_prod). Mas:

  • nome_produto, preco dependem só de id_prod;
  • id_cli depende só de id_pedido.

São dependências parciais → separa em três tabelas:

Pedido      (id_pedido PK, id_cli, nome_cliente)
Produto     (id_prod PK, nome_produto, preco)
ItemPedido  (id_pedido, id_prod, qtd)   PK (id_pedido, id_prod)

3ª Forma Normal — sem dependência transitiva

Regra: estar em 2FN + coluna não-chave não depende de outra coluna não-chave.

Na tabela Pedido: nome_cliente depende de id_cli, que depende de id_pedido. É uma dependência transitiva.

Correção: os dados do cliente saem para a tabela Cliente.

Cliente  (id_cli PK, nome_cliente)
Pedido   (id_pedido PK, id_cli FK)

O esquema em CREATE TABLE

CREATE TABLE cliente (
    id_cli       VARCHAR(6)   PRIMARY KEY,
    nome_cliente VARCHAR(100) NOT NULL
);
CREATE TABLE telefone_cliente (
    id_cli   VARCHAR(6) REFERENCES cliente(id_cli),
    telefone VARCHAR(20),
    PRIMARY KEY (id_cli, telefone)
);
CREATE TABLE produto (
    id_prod      VARCHAR(6)    PRIMARY KEY,
    nome_produto VARCHAR(100)  NOT NULL,
    preco        NUMERIC(10,2) NOT NULL CHECK (preco > 0)
);
CREATE TABLE pedido (
    id_pedido INT PRIMARY KEY,
    id_cli    VARCHAR(6) NOT NULL REFERENCES cliente(id_cli)
);
CREATE TABLE item_pedido (
    id_pedido  INT        REFERENCES pedido(id_pedido),
    id_prod    VARCHAR(6) REFERENCES produto(id_prod),
    qtd        INT NOT NULL CHECK (qtd > 0),
    PRIMARY KEY (id_pedido, id_prod)
);

Juntar tudo de volta

A "planilha" original volta com um SELECT + JOIN:

SELECT p.id_pedido, c.nome_cliente, pr.nome_produto, i.qtd
FROM   pedido      p
JOIN   cliente     c  ON c.id_cli   = p.id_cli
JOIN   item_pedido i  ON i.id_pedido = p.id_pedido
JOIN   produto     pr ON pr.id_prod  = i.id_prod;
O dado agora está uma vez só em cada lugar. Trocar o telefone do João = alterar uma linha.

A regra em 1 frase

Toda coluna depende da chave, da chave inteira, e de nada além da chave.
"da chave" = 1FN · "da chave inteira" = 2FN · "de nada além da chave" = 3FN.
