Visão geral

Projetar antes de criar

Entre "entendi o problema" e "tenho tabelas rodando" existem três etapas. Hoje vemos o mapa; as próximas aulas descem em cada uma.

Conceitual = o quê. Lógico = como em tabelas. Físico = como rápido no PostgreSQL.
Motivação

O que acontece sem projeto

Jogar tudo numa tabela só parece rápido — até dar problema:

  • o mesmo dado repetido em dezenas de linhas;
  • mudar um telefone = corrigir linha por linha;
  • não dá pra cadastrar um curso sem ter aluno;
  • apagar o último pedido apaga o cliente junto.

Projetar bem elimina essas armadilhas antes de a base crescer.

Modelo conceitual

Entidade e seus atributos

Cada entidade tem atributos. Um deles (ou um conjunto) é o identificador — vai virar a chave primária.

Tipos comuns:

  • simples: nome, idade
  • composto: endereço (rua + número + cidade)
  • multivalorado: telefones — vira outra tabela na 1FN

Do ER para as tabelas

Regras de conversão (projeto lógico):

No modelo ERVira, no banco
Entidadeuma tabela
Atributouma coluna
IdentificadorPRIMARY KEY
Relacionamento 1:NFOREIGN KEY no lado "N"
Relacionamento N:Numa tabela associativa (2 FKs)
Atributo multivaloradouma tabela à parte
Modelo lógico

A escola vira SQL

CREATE TABLE professor (
    id_professor SERIAL PRIMARY KEY,
    nome         VARCHAR(100) NOT NULL
);

CREATE TABLE disciplina (
    id_disciplina SERIAL PRIMARY KEY,
    nome          VARCHAR(100) NOT NULL,
    id_professor  INT REFERENCES professor(id_professor)   -- 1:N
);

CREATE TABLE aluno (
    id_aluno SERIAL PRIMARY KEY,
    nome     VARCHAR(100) NOT NULL
);

CREATE TABLE matricula (          -- tabela associativa (N:N)
    id_aluno      INT REFERENCES aluno(id_aluno),
    id_disciplina INT REFERENCES disciplina(id_disciplina),
    PRIMARY KEY (id_aluno, id_disciplina)
);
Próximo passo

Depois de mapear: normalizar

O esquema lógico ainda pode ter redundância escondida. A normalização é a checagem que remove isso, em três níveis:

  • 1FN — valores atômicos, sem grupos repetidos
  • 2FN — sem dependência parcial da chave
  • 3FN — sem dependência transitiva

Modelo físico

Projeto físico: desempenho

Índices
aceleram consultas; custam um pouco em INSERT/UPDATE.
Particionamento
quebra tabelas gigantes em pedaços menores.
Normalização × desnormalização
menos redundância vs. menos JOINs. É um trade-off consciente.
O físico é o único que depende do SGBD — aqui, do PostgreSQL.
