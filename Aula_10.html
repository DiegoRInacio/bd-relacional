Motivação

Nem todo mundo pode fazer tudo

Controle de acesso não é só "ter login". É definir o que cada um pode fazer dentro do banco.

Aplicação / atendente
lê e grava em algumas tabelas
Auditor
só lê — não altera nada
DBA
cria tabelas, usuários, faz backup
Princípio do menor privilégio: cada um recebe só o que precisa — nada além.
Conceito

No PostgreSQL, tudo é uma ROLE

Não existe "usuário" e "grupo" separados. Existe role, que pode:

CREATE USER ana é só um atalho para CREATE ROLE ana LOGIN.
Criar

Criando roles

-- role que loga (um "usuário")
CREATE USER ana WITH PASSWORD 'S3nh@Forte';

-- role sem login: um "grupo" de permissões
CREATE ROLE leitura;

-- colocar a Ana no grupo
GRANT leitura TO ana;

-- no psql:  \du  lista as roles e seus atributos
Senha nunca vai no código — o PostgreSQL guarda só um hash (SCRAM). Trocar depois: \password ana.
Atributos

O que a role pode ser

AtributoSignifica
LOGINpode se conectar (é um "usuário")
SUPERUSERignora todas as permissões — praticamente nunca use
CREATEDBpode criar bancos de dados
CREATEROLEpode criar / alterar outras roles
PASSWORDdefine a senha
A aplicação nunca conecta como SUPERUSER nem como o dono do banco.
Atenção

Permissão tem dois níveis

Esqueceu o USAGE ON SCHEMA? O erro é "permission denied for schema public" — mesmo com o GRANT SELECT feito.
GRANT

Permissões nas tabelas

-- uma tabela específica
GRANT SELECT ON cliente TO auditor;

-- várias operações, todas as tabelas do schema
GRANT SELECT, INSERT, UPDATE, DELETE
ON ALL TABLES IN SCHEMA public TO atendente;

-- em sequências (para o SERIAL funcionar no INSERT)
GRANT USAGE ON ALL SEQUENCES IN SCHEMA public TO atendente;
O dono da tabela já tem tudo. O GRANT serve para dar acesso aos outros.
GRANT

E as tabelas que ainda não existem?

O GRANT ... ON ALL TABLES só vale para as tabelas de agora. Para as futuras, configure o padrão:

ALTER DEFAULT PRIVILEGES IN SCHEMA public
GRANT SELECT ON TABLES TO leitura;
Boa prática

Gerencie o grupo, não a pessoa

CREATE ROLE leitura;
GRANT USAGE ON SCHEMA public TO leitura;
GRANT SELECT ON ALL TABLES IN SCHEMA public TO leitura;

-- as pessoas entram no grupo
GRANT leitura TO ana, beto, carla;

Mudou a regra? Ajusta a role leitura — os três já herdam. Entrou alguém? Só GRANT leitura TO ....

Exemplo

Dois perfis no schema clinica

-- recepção: lê, cadastra e atualiza
CREATE USER recepcionista_cli WITH PASSWORD 'Rec@2026';
GRANT USAGE ON SCHEMA clinica TO recepcionista_cli;
GRANT SELECT, INSERT, UPDATE
  ON ALL TABLES IN SCHEMA clinica TO recepcionista_cli;

-- auditoria: só lê
CREATE USER auditor_cli WITH PASSWORD 'Aud@2026';
GRANT USAGE  ON SCHEMA clinica TO auditor_cli;
GRANT SELECT ON ALL TABLES IN SCHEMA clinica TO auditor_cli;
REVOKE

Tirar uma permissão

REVOKE INSERT ON pagamento FROM recepcionista_cli;

REVOKE ALL ON ALL TABLES IN SCHEMA clinica FROM ana;

REVOKE leitura FROM beto;      -- tira do grupo
O que o GRANT dá, o REVOKE tira — na mesma granularidade (uma operação, uma tabela, um schema ou um grupo inteiro).
Na prática

Conferindo o que cada um pode

-- "virar" outra role sem sair da sessão
SET ROLE auditor_cli;
INSERT INTO paciente ...   -- ERRO: permission denied
RESET ROLE;                -- volta a ser você

-- ver os privilégios de uma tabela
\dp clinica.paciente
Juntando o semestre

Usuário + trigger + view

Permissão, trigger e view são camadas independentes — cada uma faz o seu papel.
Boas práticas

Segurança com roles

Menor privilégio
comece com nada e vá liberando o necessário
Roles de grupo
permissão no grupo, pessoas como membros
Nada de SUPERUSER na app
a aplicação usa uma role comum e restrita
Senha forte + SCRAM
e rotação periódica
Auditoria periódica
\du, \dp — revise quem tem o quê
Uma role por serviço
não compartilhe credencial entre sistemas

Pergunta pra pensar

Antes da próxima aula

Numa loja com o schema vendas (tabelas produto, venda, vendedor), monte:

  1. a role de grupo operacao: SELECT em tudo, INSERT só em venda;
  2. a role de grupo gerencia: todas as operações em tudo;
  3. o usuário joao em operacao e maria em gerencia.

Não esqueça o USAGE ON SCHEMA nem o padrão para tabelas futuras.
